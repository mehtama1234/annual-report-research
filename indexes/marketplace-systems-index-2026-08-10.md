The point is to make the subtype map sortable by:

- marketplace system type
- subtype family
- source-taxonomy sector and industry
- trust or coordination source
- repeat behavior
- frequency band
- trust intensity
- physical embedding
- second monetization layer
- membership role
- monetization side

## Highest-confidence uses

- sort marketplace names by trust structure instead of by old sector label
- sort the lane by subtype family, frequency band, and trust intensity
- separate creator trust, recommerce-liquidity trust, and host-guest booking trust on one page
- separate merchant-heavy OTA orchestration, loyalty-thickened travel intermediation, and decentralized host-guest travel trust on one page
- separate lighter trust marketplaces from denser logistics and retailer-enablement systems
- compare where membership is central, secondary, or largely absent
- identify which names are most physically embedded in fulfillment or routing
- separate seller-weighted, retailer-weighted, merchant-weighted, and buyer-booking monetization patterns

## Current best next moves

1. Reuse the direct `Etsy` versus `eBay` versus `Airbnb` comparison first when the question is whether a marketplace belongs closer to creator trust, recommerce trust, or host-guest booking trust.
2. Reuse the direct `Booking` versus `Expedia` versus `Airbnb` split first when the question is whether a travel platform belongs closer to OTA orchestration, loyalty-thickened intermediation, or decentralized host-guest trust.
3. Add a narrower hierarchy file later only if the travel, local-demand, and trust subtypes become crowded enough to need a second dedicated marketplace-family screen.
4. Reuse this pattern for a retail-system index or a trust-marketplace-only index if the blind-spot lane keeps expanding.
